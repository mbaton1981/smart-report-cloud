# Независимое аварийное восстановление SmartReport

## Что хранить раздельно

- В личном OneDrive владельца, папка **SmartReport-Recovery**:
  зашифрованные `SmartReport-<UTC>-<случайный ID>.srbackup`,
  открытая утилита `portable_recovery.py`, зависимости
  `RECOVERY-REQUIREMENTS.txt`, проверенный набор `VERIFIED-DEPENDENCIES.txt`,
  эта инструкция и результаты `verification.json`.
- В менеджере паролей владельца: **пароль восстановления SmartReport**.
  Не сохранять пароль в OneDrive, ярлыке, скрипте или переписке.
  Доступ к менеджеру и его MFA/аварийным кодам должен восстанавливаться
  без нынешнего компьютера и Windows-профиля. Это проверяет владелец.
- Доступ к OneDrive/Microsoft account и Render также должен быть доступен
  независимо от потерянного компьютера; коды восстановления хранить отдельно.

Внутри каждого зашифрованного комплекта находятся согласованный снимок
серверной SQLite-базы, оригиналы документов из этого снимка, серверный ключ
карточек, необходимая конфигурация и совместимый код коммита
`5abdb032b0182e0b1dcf2d2cb4ddd084c62428a2`. Сам пароль не включается.
Формат SRBACK01: AES-256-GCM, случайные соль/nonce, Scrypt
`N=131072, r=8, p=1`; содержимое и заголовок аутентифицированы.
Требуется уникальный пароль от 16 символов; предпочтителен длинный случайный
пароль, созданный менеджером.

Это отдельный инструмент, не обновление рабочего клиента или сервера.
DPAPI используется только для первоначального чтения существующей защищённой
локальной копии ключа на исходном компьютере. Для расшифровки `.srbackup`
DPAPI, старый Windows-профиль и старая программа не нужны.

## Создание новых версий на нынешнем компьютере

Запустить ярлык **SmartReport — резервная копия OneDrive**.
Ввести пароль из менеджера дважды и подтвердить отдельное хранение.
Кнопка **Создать копии и проверить восстановление** создаёт две свежие
серверные версии, проверяет шифрование и восстановление каждой в отдельном
Python venv. Рабочая база не заменяется, финансовые действия не выполняются.
Авторизованные запросы резервирования могут штатно обновлять служебную
метку использования токена; это не изменение рабочих записей или расчётов.
Среда проверки получает пустые пути профиля, использует только комплект и
введённый пароль, сетевые соединения в проверочном процессе блокируются.
Это изоляция процесса и окружения, **не отдельная VM и не другой компьютер**.

Старые версии не перезаписываются и автоматически не удаляются.
Неверный пароль, повреждение, неполная загрузка или ошибка проверки
не уничтожают предыдущие файлы. Структурно целая база всё равно может
содержать ошибку пользователя — поэтому нужны версии за разные даты,
а не только две копии в один день. Автоматического расписания нет:
делать копии регулярно и после значимых изменений.
Пароль не меняйте без плана: старые версии потребуют прежнего пароля.

### Обязательно подтвердить загрузку в облако

1. Нажать значок облака OneDrive в области уведомлений Windows.
   Если требуется, войти в **свой личный** Microsoft account.
2. Открыть папку **OneDrive → SmartReport-Recovery**.
   Дождаться завершения загрузки; красный крест или «Ожидание синхронизации»
   означают, что внешняя копия ещё не готова.
3. На сайте **onedrive.live.com**, лучше с телефона/другого устройства,
   открыть **Мои файлы → SmartReport-Recovery**. Проверить наличие и размер
   обоих `.srbackup`, утилиты и инструкции. Для проверки скачать один файл
   в отдельную папку и сравнить SHA-256 с `verification.json`.
4. Пока это не подтверждено, локальная папка OneDrive не считается
   доказанной внешней копией. `onedrive_cloud_upload_confirmed: false`
   в автоматическом отчёте честно обозначает именно это ограничение.

Не использовать общедоступные ссылки. Ограничить доступ к папке владельцем
и отдельно назначенными ответственными лицами. OneDrive — не неизменяемый
архив: удаление/шифровальщик может синхронизироваться. Дополнительная
отсоединённая копия и политика сроков хранения остаются обязанностью владельца.

## Восстановление на новом компьютере

Потребуются доступ к OneDrive, пароль из менеджера, Python 3.12+ и интернет
для установки зависимостей (на время самой проверки сеть не используется).
В PowerShell, в скачанной папке:

```powershell
python -m venv recovery-env
.\recovery-env\Scripts\python.exe -m pip install -r .\VERIFIED-DEPENDENCIES.txt
.\recovery-env\Scripts\python.exe -I .\portable_recovery.py ".\SmartReport-<имя версии>.srbackup" --verify-only
```

Ввести пароль в скрытом приглашении терминала, **не в аргументах команды**.
Успешный JSON должен сообщить `database_integrity: true`,
`all_business_table_hashes_unchanged: true`, `wrong_key_denied: true`,
`dpapi_used: false`. Утилита проверяет все непустые зашифрованные карточки,
запускает совместимый сервер только на временной копии и проверяет чтение.
Проверка не закрывает зарплату, не отмечает выплаты и не меняет «Баланс».

Для извлечения в **новую** закрытую папку вне OneDrive:

```powershell
.\recovery-env\Scripts\python.exe -I .\portable_recovery.py ".\SmartReport-<имя версии>.srbackup" --destination "C:\SmartReport-Restore-New"
```

Не выбирать рабочую папку сервера. Папка назначения не должна существовать.
На Windows создавать её внутри диска/профиля с ограниченным доступом;
на Linux файлы получают права `0600`, каталоги `0700`.
Извлечённые конфигурация и ключ — **секреты в открытом виде**:
не прикладывать их к письмам, не возвращать в синхронизируемую папку,
не показывать в терминале. После переноса секретов и завершения восстановления
удалить только конкретную временную папку с расшифрованными данными.

## Возвращение сервера в работу

Выполняется администратором инфраструктуры после проверки:

1. Сохранить отдельный актуальный снимок сервера, если он ещё доступен.
   Восстановление старого комплекта не должно затирать более новые записи.
   Сверить время выбранной версии и отдельно согласовать с владельцем
   любые потери/слияние записей после этого времени.
2. Развернуть код из `source` на отдельном сервисе/диске с нужными
   зависимостями, настроить HTTPS, persistent storage и конфигурацию.
3. Использовать `backup/server_snapshot.db` и **ключ из того же комплекта**.
   Ключ перенести в закрытый файл persistent disk с правами `0600`,
   подключить через `SMARTREPORT_EMPLOYEE_CARD_KEY` без печати значения.
   `DATABASE_PATH` и `SMARTREPORT_DOCUMENTS_DIR` указывают на новые пути.
   Не переносить старые абсолютные пути Windows/Render вслепую.
4. Если есть оригиналы документов: файлы в `backup/documents` названы
   по ID для резервирования. По `backup/manifest.json`, таблицам
   `expense_document_attachments` / `expense_documents` восстановить
   соответствие `stored_name` и проверить SHA-256. Не запускать рабочий
   сервис с потерянными оригиналами. Приёмочный комплект от 23.10
   проверялся при нулевом количестве серверных оригиналов.
5. Проверить карточки, права и отчёты, затем явно переключить клиентов
   на восстановленный сервис. Отозвать старые токены/пароли при подозрении
   на компрометацию, а не просто потерю устройства. Auto-Deploy оставить Off.

**Не генерировать новый ключ вместо утраченного:** он не расшифрует карточки.
Не использовать rc8 как безопасный откат карточек и не подставлять старую
базу поверх действующего сервера.
