# Карточки сотрудников

## Работа в программе

В существующем справочнике **Сотрудники** выберите строку и нажмите
**Открыть карточку**. Разделы: основные сведения, персональные данные,
контакты, банк. Неизвестные поля оставляйте пустыми. Номер, индекс,
clearingnummer и номер счёта — текст: начальные нули сохраняются.
Форматные предупреждения не запрещают сохранение неполной карточки;
некорректную дату исправьте либо очистите.

ФИО и текущая зарплатная ставка берутся из существующего справочника.
Ставка в карточке только для просмотра. Переименование здесь отключено:
старые смены программы связаны по имени, а не по внешнему ключу employee_id.
Локальный числовой ID не меняется; серверный ID привязывается к нему один
раз по однозначному соответствию. Неоднозначность или изменение личности
не приводят к автоматической перепривязке и созданию дубля.

Статус **Уволен** использует существующую деактивацию, не удаляет сотрудника
и историю. Даты сами по себе не меняют статус. Изменение статуса явно
сохраняется пользователем и синхронизируется существующим событием статуса;
зарплатная ставка при этом не меняется.

Для иностранного счёта выберите **Иностранный счёт (IBAN/BIC)**. Заполненность
не требует clearingnummer и шведского номера счёта. Персональный номер
может отсутствовать — в передаче будет обозначен пропуск, учёт не блокируется.
Индикатор «Не хватает данных» объясняет поля во всплывающей подсказке.
В обычном списке номера и счета вообще не показываются.

После изменения банковских полей сервер очищает дату подтверждения —
даже если клиент одновременно прислал дату. Сначала сохраните новый счёт,
проверьте его у сотрудника, затем нажмите **Подтвердить актуальность сегодня**
и **Сохранить**. Это не выплата и не начисление. История показывает автора,
время, версию и названия изменённых полей, но не прежние/новые значения.

**Данные для бухгалтера** предлагает одного сотрудника, выбранные строки
(Ctrl/Shift) или всех действующих. Пропуски и сомнения в формате показаны
до просмотра и в PDF. PDF не содержит смен, OB, клиентских цен или
зарплатных сумм. Сначала открывается встроенный чёткий просмотр; сохранение
и печать отдельно и повторно проверяют права.

## Доступ и хранение

- Доступ только по действующему личному bearer-токену роли `admin` или
  `accountant`. Общий sync-ключ, браузерная cookie, обычный пользователь
  и отозванный токен не дают доступа. Ответы `no-store`.
- Администратор назначает отдельный логин бухгалтера через **Доступ бухгалтера…**
  (пароль не короче 12 символов). Существующий логин не переназначается.
  Там же можно отозвать доступ со всеми токенами. Пароль передавайте
  отдельно защищённым каналом.
- Бухгалтер входит через обычное окно входа, но получает только ограниченный
  список и карточки, не финансовое окно. Сервер не допускает его к финансовому
  sync API, полной резервной копии или назначению другого бухгалтера.
- Карточки работают онлайн. При отсутствии сервера, прав или ключа они
  закрыты; обычный учёт администратора и предварительные отчёты не зависят
  от наличия реквизитов. Офлайн-редактирования/автоматического слияния нет.
  При конфликте версий сохранение отклоняется, введённое остаётся в окне;
  откройте актуальную карточку и согласуйте изменения. Ответ об ошибке сети
  не считается подтверждением записи.
- Сервер хранит Fernet-шифротекст (аутентифицированное шифрование) в той же
  строке `meta_employees`; связь ID включена в зашифрованный конверт.
  Локальная строка `employees` получает только этот шифротекст, версию и
  серверный ID после успешного запроса. Ключ расшифровки клиенту не выдаётся,
  кэш не открывается офлайн и не попадает в общий каталог сотрудников.
- Передача — HTTPS с проверкой сертификата; HTTP разрешён клиентом только
  для localhost-тестов. Перенаправления защищённых запросов запрещены.
- PDF строится/просматривается в памяти, временный открытый PDF не создаётся.
  Если QtPdf недоступен, конфиденциальный экспорт закрывается с объяснением,
  а не передаёт незашифрованный файл внешнему приложению.
- Сохранённый по явному запросу PDF и задания печати **не шифруются этой
  функцией**. Перед сохранением есть предупреждение. Храните их в защищённой
  папке, используйте защищённую передачу и контролируйте очередь принтера.
  Данные уже открытого окна нельзя «отозвать из памяти» удалённо; права
  повторно проверяются при открытии, сохранении, экспорте и печати.

## Подготовка сервера — только после согласования

Новая версия клиента со старым сервером показывает, что требуется
согласованное обновление; карточки до него недоступны. Сервер в рамках
локальной установки **не обновляется**. Auto-Deploy должен оставаться Off.

1. Сделать свежий согласованный snapshot БД/настроек, сохранить текущий код.
2. В защищённых настройках сервера создать отдельный секрет
   `SMARTREPORT_EMPLOYEE_CARD_KEY`: Fernet key, сгенерированный
   `cryptography.fernet.Fernet.generate_key()`. Не писать ключ в git, лог,
   чат или обычную резервную копию БД. Не использовать пароль или SECRET_KEY.
3. Сохранить ключ отдельно в защищённом хранилище владельца и проверить
   восстановление тестового шифротекста. Без ключа восстановленная БД
   не открывает реквизиты. Не генерировать новый ключ при каждом запуске.
4. Установить объявленные зависимости, развернуть согласованный коммит.
   Проверить существующую настройку доверенного прокси (`TRUSTED_PROXY_HOPS`):
   сервер должен видеть HTTPS после TLS-терминации. Защищённый API отклоняет
   небезопасный внешний HTTP; локальное исключение требует loopback-адреса
   и loopback-host. Не доверять произвольным forwarded-заголовкам.
   Миграция добавляет `card_cipher`, `card_version` в `meta_employees`,
   метаданные аудита и идемпотентных операций. В клиенте добавляются
   `card_cipher`, `card_version`, `card_server_id` в `employees`. Начальные
   значения NULL/0; старые поля, ID, смены и расчёты не переписываются.
5. Проверить administrator/accountant/user, отказ при неверном dataset,
   повтор записи, конфликт, backup+restore с отдельным тестовым ключом.
   Затем назначить реального бухгалтера явным действием администратора.

Зарезервируйте зашифрованную БД обычным механизмом резервного копирования.
Карточки в копии остаются шифротекстом; аудит содержит только метаданные.
Это не шифрование всей старой БД: остальной существующий учёт не менялся.
Защитите диски и доступ к копиям средствами ОС/хранилища. Не помещайте
ключ и копию БД в один незащищённый архив.

Смена ключа без миграции шифротекста запрещена: потеря ключа означает
потерю доступа к реквизитам. Ротация требует отдельной процедуры
резервирования, расшифровки старым ключом и перешифрования новым; кнопки
автоматической ротации нет. Проверяйте восстановление с действующим ключом.

Откат — замена программы на совместимую предыдущую версию с сохранением
**текущей** БД и добавленных колонок/таблиц. Прежний код не открывает
карточки, но не должен удалять шифротекст. Не восстанавливайте старую БД
поверх новых записей. При сбое — snapshot текущего состояния и исправление
вперёд. Полный откат закрытых зарплат по-прежнему подчинён прежним блокировкам.

## Организационные решения владельца

Изменения не являются заявлением о полном соответствии GDPR. Владельцу
нужно определить правовое основание/уведомление сотрудников, минимальный
набор собираемых данных, список уполномоченных лиц, сроки хранения,
порядок исправления/удаления, хранение старых резервных копий и PDF,
защищённую передачу бухгалтеру, договорённости с хостингом/бухгалтером,
защиту рабочих мест, доступ к ключам и действия при инциденте.
Каждому человеку нужны отдельные учётная запись приложения и профиль ОС:
общий Windows-профиль не защищает от доступа владельца этого профиля,
снимков экрана, администратора компьютера или вредоносной программы.
Автоматического удаления сотрудников/карточек и сроков хранения здесь нет.
